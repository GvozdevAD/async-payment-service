# ADR 0005. Идемпотентность создания платежа

- Статус: Accepted
- Дата: 2026-07-10

## Контекст

`POST /payments` принимает заголовок `Idempotency-Key`. Повтор запроса (ретрай
клиента, дубликат от прокси) не должен создавать второй платёж. При конкурентных
одновременных запросах с одним ключом возможна гонка.

## Решение

`idempotency_key` — колонка с **UNIQUE-ограничением** на `payments`. В
`app/services/payment.py::create_payment`:

1. Предварительная проверка `get_by_idempotency_key` — быстрый путь для явного
   повтора.
2. Вставка платежа + outbox в одной транзакции.
3. Гонку ловим на `commit`: `IntegrityError` → `rollback` → повторное чтение по
   ключу → возврат уже созданного платежа. Если записи нет — ошибка не про
   идемпотентность, пробрасываем.

## Альтернативы

- **Только предварительный SELECT** — есть окно гонки между SELECT и INSERT для
  конкурентных запросов.
- **Advisory lock / SELECT FOR UPDATE по ключу** — сериализует запросы, но
  дороже и сложнее, чем «положиться на UNIQUE + обработать IntegrityError».
- **Upsert `ON CONFLICT`** — усложняет возврат «создан vs существовал» и
  атомарную запись связанного outbox.

## Последствия

- Корректность при конкуренции обеспечена БД (единый источник истины —
  UNIQUE-индекс).
- Ответ детерминирован: один и тот же ключ → один и тот же платёж.
- Идемпотентность гарантируется только на **создании**; потребитель вебхука всё
  равно обязан быть идемпотентным по `payment_id` (at-least-once дальше по цепочке).
