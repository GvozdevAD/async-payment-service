# ADR 0001. Outbox pattern для публикации событий

- Статус: Accepted
- Дата: 2026-07-10

## Контекст

`POST /payments` должен атомарно создать платёж и гарантированно опубликовать
событие `payment.new` в RabbitMQ. Прямая публикация в брокер внутри
HTTP-обработчика приводит к рассинхрону: коммит в БД прошёл, а publish упал (или
наоборот) — событие теряется или дублируется без записи-источника правды.

## Решение

Запись платежа и запись в таблицу `outbox` выполняются в **одной транзакции**
(`app/services/payment.py::create_payment`). Отдельный поллер
(`OutboxPublisher`) читает `status = PENDING` пачками с
`SELECT ... FOR UPDATE SKIP LOCKED` (`app/repositories/outbox.py`), публикует в
RabbitMQ с ретраями и переводит запись в `PUBLISHED` / `FAILED`.

## Альтернативы

- **Прямой publish в обработчике** — нет атомарности «БД + брокер», события
  теряются при сбое.
- **CDC / Debezium poll на WAL** — надёжно, но тяжёлая инфраструктура для
  тестового сервиса.
- **Distributed transaction (2PC)** — сложно, плохо масштабируется, не
  поддерживается связкой Postgres + RabbitMQ из коробки.

## Последствия

- Гарантия доставки **at-least-once**: publish может повториться, потребитель
  обязан быть идемпотентным (см. ADR 0005).
- Появляется лаг публикации, равный интервалу поллинга.
- Нужен процесс-поллер и мониторинг `outbox_pending` (метрика).
