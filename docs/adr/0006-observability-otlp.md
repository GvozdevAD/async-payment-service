# ADR 0006. Observability: единый OTLP-пайплайн, метрики только через OpenTelemetry

- Статус: Accepted
- Дата: 2026-07-10

## Контекст

Сервис — несколько процессов (API, publisher, consumer, dispatcher). Нужны
трейсы и метрики со всех. Возможные пути экспорта метрик: Prometheus-эндпоинт
`/metrics` (pull) либо OTLP-экспорт в коллектор (push), как и трейсы.

## Решение

Единый OpenTelemetry-пайплайн (`app/core/telemetry.py`, `app/core/metrics.py`):
трейсы и метрики уходят по **OTLP/gRPC** в otel-collector, оттуда — в бэкенды
(Prometheus для метрик и т.д., см. `dockerfiles/otel-collector`). Метрики
определяются как OTel-инструменты (Counter/Histogram/ObservableGauge). Отдельного
HTTP-эндпоинта `/metrics` в приложении **нет**. Всё включается флагом
`OTEL_ENABLED` (по умолчанию `false`, чтобы не требовать коллектор локально/в
тестах).

## Альтернативы

- **`prometheus_client` + `/metrics` scrape** — привычно, но добавляет второй,
  отдельный от трейсов путь телеметрии и HTTP-эндпоинт в каждый процесс (у
  publisher/consumer HTTP-сервера нет).
- **Прямой экспорт в вендор** — привязка к бэкенду; коллектор развязывает
  приложение и хранилище.

## Последствия

- Единая модель и конфигурация для трейсов и метрик; смена бэкенда — вопрос
  конфигурации коллектора, не кода.
- Для метрик нужен запущенный collector; при `OTEL_ENABLED=false` инструменты —
  no-op (нулевой оверхед в тестах).
- Non-HTTP процессы экспортируют метрики без необходимости поднимать scrape-эндпоинт.
