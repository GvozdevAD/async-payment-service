# ADR 0003. Второй транзакционный outbox для вебхуков (`webhook_deliveries`)

- Статус: Accepted
- Дата: 2026-07-10

## Контекст

Consumer обрабатывает `payment.new`: дергает gateway и обновляет статус платежа.
После этого нужно доставить вебхук клиенту. Если отправлять HTTP прямо из
consumer, доставка вебхука связана с обработкой сообщения: падение HTTP приводит
к nack/повторной обработке платежа, а долгие ретраи вебхука держат consumer.

## Решение

Consumer в **той же транзакции**, что и обновление статуса платежа, пишет запись
в таблицу `webhook_deliveries` (`app/services/payment_processor.py::_enqueue_webhook`,
`app/repositories/webhook_delivery.py`). Отдельный `webhook-dispatcher` поллит
due-записи (`next_attempt_at <= now`, `FOR UPDATE SKIP LOCKED`), делает HTTP,
ретраит с экспоненциальным backoff и переводит запись в `DELIVERED`/`FAILED`.
Идемпотентность enqueue — `ON CONFLICT (payment_id) DO NOTHING`.

## Альтернативы

- **Отправка HTTP прямо из consumer** — смешивает обработку платежа и доставку
  вебхука; ретраи вебхука влияют на throughput очереди.
- **Отдельная очередь RabbitMQ для вебхуков** — рабочий вариант, но потребовал бы
  ещё одну транзакционную границу «БД → брокер»; повторно используем уже
  доказавший себя outbox-механизм на БД.

## Последствия

- Доставка вебхука декуплена от обработки платежа и переживает рестарты.
- Сознательное **дублирование механизма** outbox (события + вебхуки) —
  цена за единообразие и durability.
- At-least-once и здесь: дубликат вебхука возможен при падении между успешным
  HTTP и `mark_delivered` (см. ADR 0008 и Trade-offs).
