# ADR 0004. DLQ через `x-retry-count` + nack/requeue

- Статус: Accepted
- Дата: 2026-07-10

## Контекст

Обработка `payment.new` может падать по транзиентным причинам (gateway/БД
временно недоступны) и по неустранимым (платёж не найден, невалидное сообщение).
Нужен ограниченный ретрай транзиентных ошибок и отправка «ядовитых» сообщений в
DLQ, без бесконечного цикла переобработки.

## Решение

В `app/consumer/delivery.py`:

- **Poison / ValidationError** → сразу `RejectMessage(requeue=False)` → DLQ.
- **Транзиентная ошибка** → счётчик попыток хранится в заголовке
  `x-retry-count`; пока `< CONSUMER_MAX_ATTEMPTS` — `NackMessage(requeue=True)`;
  на исчерпании — `RejectMessage(requeue=False)` → DLQ.
- Fallback на брокерский `x-death`, если своего заголовка ещё нет.

DLQ — очередь `payments.new.dlq` (`RABBITMQ_PAYMENTS_NEW_DLQ`).

## Альтернативы

- **Quorum queue + `x-delivery-limit`** — брокер сам считает попытки и роняет в
  DLQ; надёжнее, но привязывает к типу очереди и версии RabbitMQ.
- **Delayed-exchange для backoff** — сложнее топология ради задержек, которых для
  этого кейса достаточно на уровне requeue.

## Последствия

- Простая, портируемая логика ретраев на уровне приложения.
- `requeue=True` возвращает сообщение в голову очереди без задержки — при
  устойчивой ошибке попытки исчерпываются быстро (это приемлемо: реальные
  задержки закрывает backoff вебхук-диспетчера).
- Счётчик в заголовке зависит от того, что consumer его проставляет перед nack.
