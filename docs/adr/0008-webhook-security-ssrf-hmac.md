# ADR 0008. Безопасность вебхуков: SSRF-защита и HMAC-подпись

- Статус: Accepted
- Дата: 2026-07-11

## Контекст

`webhook_url` задаёт клиент, а исходящий HTTP-запрос выполняет наш сервис
(webhook dispatcher). Это создаёт два риска:

1. **SSRF.** Через `webhook_url` можно заставить сервис обратиться во внутреннюю
   сеть: `http://169.254.169.254/` (облачные метаданные), `http://localhost`,
   приватные диапазоны, служебные порты. DNS-имя может резолвиться в приватный
   адрес как сразу, так и позже (DNS rebinding).
2. **Подделка/искажение доставки.** Получатель вебхука не может отличить наш
   запрос от постороннего и не видит, что тело не было изменено по пути.

## Решение

### SSRF-защита (`app/core/url_guard.py`)

Проверка в два этапа:

1. **При создании платежа** (`POST /payments`) — без DNS: разрешённая схема
   (`WEBHOOK_ALLOWED_SCHEMES`), отсутствие `user:pass@`, допустимый порт
   (`WEBHOOK_ALLOWED_PORTS`). Нарушение → `422 unsafe_webhook_url` (fail-fast,
   до записи в БД).
2. **Перед доставкой** (dispatcher) — резолвинг хоста и блокировка
   non-public адресов: private, loopback, link-local, reserved, multicast,
   unspecified (`WEBHOOK_BLOCK_PRIVATE_NETWORKS=true`). Повторная проверка
   именно перед отправкой закрывает DNS rebinding. Заблокированная доставка
   помечается `failed` и учитывается метрикой
   `webhook_delivery_total{outcome="blocked"}`.

### HMAC-подпись (`app/core/signing.py`)

При заданном `WEBHOOK_SIGNING_SECRET` (≥16 символов) и
`WEBHOOK_SIGNATURE_ENABLED=true` каждый запрос подписывается HMAC-SHA256 и
снабжается заголовками:

- `X-Webhook-Signature: t=<unix_ts>,v1=<hex_hmac>`
- `X-Webhook-Timestamp: <unix_ts>`

Подпись считается по `f"{timestamp}.".encode() + body`, где `body` — ровно те
байты, что уходят по сети (тело сериализуется один раз). Формат
`t=...,v1=...` оставляет место для ротации схемы (`v2`, несколько активных
секретов) без ломающих изменений. Timestamp в подписи даёт получателю защиту
от replay.

Пример верификации на стороне получателя:

```python
import hashlib
import hmac

signed = f"{timestamp}.".encode() + request.body
expected = hmac.new(secret.encode(), signed, hashlib.sha256).hexdigest()
assert hmac.compare_digest(expected, signature_v1)  # constant-time
# + отклонить запрос, если timestamp слишком старый (защита от replay)
```

## Альтернативы

- **Allowlist доменов вместо блокировки по IP.** Строже, но требует, чтобы
  клиенты заранее регистрировали домены — не подходит для открытого API.
  Блокировка приватных диапазонов даёт разумный дефолт без регистрации.
- **mTLS вместо HMAC.** Сильнее, но дороже в эксплуатации (управление
  сертификатами на стороне клиента). HMAC с общим секретом закрывает
  аутентичность и целостность при минимальной интеграции.
- **Подпись только тела (без timestamp).** Проще, но не защищает от replay.

## Последствия

- Подпись активируется только при заданном секрете — сервис поднимается без
  обязательной конфигурации, но в production секрет обязателен.
- По умолчанию разрешены `https` и `http`; для боевой среды схему логично
  сузить до `["https"]` через `WEBHOOK_ALLOWED_SCHEMES`.
- Resolve хоста перед доставкой добавляет один DNS-lookup на попытку и может
  отклонить легитимный вебхук за NAT/VPN — это осознанный trade-off в пользу
  безопасности, регулируемый флагом `WEBHOOK_BLOCK_PRIVATE_NETWORKS`.
- Остаточный риск: rebinding между резолвом и TCP-коннектом. Полное закрытие —
  пин на резолвнутый IP через кастомный httpx transport (вынесено на будущее).
